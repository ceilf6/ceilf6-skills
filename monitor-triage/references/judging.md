# 判定口径

每条告警只落一个 agent 结论：能修 / 不能修。判定只在 `walk` 给出 `unjudged` 时做，落档后作为缓存复用；agent 判不能修的条目以跳过清单呈现给用户兜底，用户已拒绝的条目保留在台账中但不再呈现。

`walk` 给出 `skip/bucket` 的条目（服务端错误码、网络、宿主与 Native 桥三类）不做判定、不读代码：这三类里 web 侧能做的通常只是 catch、降级或能力探测，是否值得做由用户看整桶摘要后捞回决定。捞回后它就是普通候选，按本文判定口径走。同文案族（`family_key` 相同）里读过一条的调用链，其余各条调用链相同时一并 `judge`，理由注明「同文案族，调用链同 <issue_id>」。

版本分布只能作为排查线索，不能单独用来排除候选。issue 只在低版本出现、暂未在高版本观测到，不代表高版本不会出现；没有修复 commit、相关代码路径已移除或 feature gate 已排除触发等正向证据时，继续按普通候选走查和判定。

## 退役能力：会中笔记

会中笔记 / 个人笔记能力已下线，与该能力直接相关的 issue 不纳入候选，固定判不能修。证据必须能把问题锚到具体页面、能力或调用链，例如 `GET_USER_GUIDE_REQUEST`、Native command `7507`、会中笔记引导状态查询；理由写 `退役能力：会中笔记已下线；证据：<页面、能力或调用链>`。该口径对 web-monitor 和 Lark 来源一致，命中后不再继续分析用户影响、改法或已有处理情况。

这是能力边界，不是关键词黑名单。不得只凭「笔记」「纪要」「总结」等字样排除；妙记、AI 纪要 / 会后纪要、录音页及其它仍在使用的总结能力继续按普通口径判断。证据不足以区分会中笔记与这些近邻能力时，也继续普通判定。

## 能修

两条同时成立才判能修：

1. **web 侧表现有问题。** 页面崩溃或白屏、功能不可用、展示错误、交互卡住（loading 不复位、ErrorBoundary 吞掉整块内容），或可观测的性能退化。证据来自堆栈所在的调用链（错误有没有逃逸、失败后 UI 进入什么状态）、web-monitor 事件 context 或用户反馈。底层（服务端、网络、宿主、rust-sdk）真实失败时，web 展示失败态、空态或重试入口是正确行为，不算表现有问题。
2. **候选所属仓能消除或缓解它。** biz-vc-web 候选看 `ai-summary/` 或 `packages/`，biz-vc-pc 候选（lark_vc_pc）看 `packages/biz-vc-*/src`。改法包括修缺陷（空值、竞态、读写 key 不一致等）、失败降级（兜底 UI、重试、跳过非关键数据）、宿主未提供 API 时走替代路径。

只改上报方式的改动不构成能修：加 catch 但表现不变、把 error 降成 warn、停止 captureError、去掉无消费者的调用，消除的是告警，不是用户侧问题。

### AI 产出的 JSON 形状不符合类型声明

鱼骨图图表 `chart.data`、流程图节点、表格行列这类由模型生成、前端 `JSON.parse` 后直接渲染的数据，TypeScript 类型对它没有运行时效力，字段偶尔会以错误形状出现（典型：声明为 `string[]` 的 `desc` 输出成字符串，`desc.length > 0` 守卫放行后 `.map` 抛错，整张图被 ErrorBoundary 吞掉）。整张图消失是用户侧问题，判能修，改法口径固定（2026-10-20 宙哥裁定）：

- 解析后用 `Array.isArray` / `typeof` 按类型声明筛一遍，形状正确的部分照常渲染，主要内容能展示就尽量展示出来。
- 形状不符的字段直接丢弃，不做类型强转或猜测性归一（例如不把字符串包成单元素数组）：模型输出不符合约定时无法确认它表达的是否是预期含义，宁可少显示一段说明，也不展示可能错误的内容。
- 丢弃只到字段级，不影响同一张图里其它节点或其它字段；整块内容都无法按声明解析时，才允许整张图不展示。
- 筛选放在解析处一次做完（同目录先例：`compare-table-json.tsx`、`bar/index.tsx`），不在渲染点逐处补判断。

### 误报与纯噪音判不能修

误报表示「实际处于允许或预期状态，但检测规则把它当成异常」；纯噪音表示错误已在调用点 catch 并降级，用户侧表现正常。两者都判不能修，理由写明用户侧表现正常的证据，例如「catch 后返回空列表，多设备提醒不展示，页面其余功能正常」。收紧检测条件、降级上报这类只消告警的改动不派单；要治理噪音由用户捞回后单独决定。

典型误报：

- 页面或 WebView 已隐藏，仍用可见态的布局、滚动或截图规则检查并报错
- 初始化、卸载、动画切换等允许的瞬态，被轮询或连续计数规则判成稳定故障
- 代码主动 `captureException` / `report*Error` 的事件，实际只是在记录已拦截、已降级或预期内状态

### 录音页（minutes_record）候选

这个 bid 的候选是录音页里挂载的 ai-summary 视图抛出、经录音 SDK 转报的，判定口径与 ai_summary 完全一致，只有定位方式不同（见 SKILL.md 第 4 步：按 `message_core` 文案 grep）。两点特殊：

- 「sourcemap 没解析」「堆栈只有 CDN chunk」不是判不能修的理由；`project_frames>0` 已经说明调用链在 ai-summary bundle 里。
- `project_frames=0` 且文案在 `ai-summary/`、`packages/` 都 grep 不到，再去 biz-vc-mm-web 的 `apps/record/record-sdk` 确认抛出点；确认在那里才判不能修，理由写 `调用点在录音 SDK（biz-vc-mm-web），ai-summary 无调用点`。

「请求确实超时 / 网络确实失败，原因来自用户设备或环境」：告警忠实表达了真实失败、web 侧只是把失败展示出来时判不能修。`source_type=manual`、`[warn]`、错误已被 catch、未崩溃，都是用户侧表现正常的信号；没有相反证据时按误报判不能修。

```bash
node <skill>/scripts/state.mjs judge --dir <state> --issue-id <id> --fixable yes --reason "<用户侧问题一句话 + 点位与改法一句话>"
```

## 判不能修之前

1. 沿**完整堆栈**找出项目调用点，不只看最新帧。最新帧在宿主、CDN、`[native code]`、`native-resource://`、rust-sdk 封装（`node_modules/@lark/services`）时，往上找第一个 `ai-summary/` 或 `packages/` 帧；整条栈都没有，再取同 issue 的其他事件看。
2. 说明「能修」两条里哪一条不成立：是用户侧表现正常，还是本仓没有改动点。
3. 理由写一句话、点名责任层或给出表现正常的证据：
   - `master 已修（<commit>），线上 <release> 未带上`：`git -C <repo> log -S'<关键片段>' origin/master --oneline` 查到提交，且线上 `release_dist` 主版本早于该提交进入的 builds 分支版本。
   - `同缺陷已派单 <issue_id>`：调用链汇到那张单的改动范围（典型是超时类错误落在共享 throw 点），用 `--same-as`。同文案的 issue 不自动继承已派单或已判定那条的结论，要读过调用链确认相同才归过去。
   - `调用点在宿主内置脚本，ai-summary 无调用点`。
   - `误报 / 已拦截：<catch 位置与降级后的表现>，用户侧无影响`。
   - `底层真实失败，失败态是忠实展示：<rust-sdk / 服务端 / 网络 / 宿主>，web 侧没有更合理的降级点`。

```bash
node <skill>/scripts/state.mjs judge --dir <state> --issue-id <id> --fixable no --reason "<责任层或表现正常的证据一句话>"
node <skill>/scripts/state.mjs judge --dir <state> --issue-id <id> --same-as <已派单 issue_id> --reason "同缺陷已派单 <issue_id>：<一句话>"
```

只写来源、不带证据的理由不合格：「宿主问题」「服务端错误码」「warn 级日志」「页面在豆包」「这是误报」。写误报要带 catch 位置或表现正常的依据；写底层失败要说明 web 侧为什么没有更合理的降级点。豆包移动端是 ai-summary 的正式入口，不因为页面在豆包就跳过。

## 拿不准

判不能修，理由写明缺哪项证据（用户侧表现，或本仓改动点），进跳过清单由用户捞回。走查只呈现有把握是真问题的候选；漏判靠用户读跳过清单兜底。

## 用户决定优先

用户捞回（`verdict.by=user`）的条目 agent 不改判，`judge` 会拒绝；用户拒过的条目只能由用户捞回。
