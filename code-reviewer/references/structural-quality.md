# 结构质量审查

用这份清单判断变更是否让代码库更难维护。它不是风格审查；只有当结构退化会影响理解、扩展、验证或合并风险时，才产出 finding。

## 核心原则

评审时主动寻找能保持行为不变但显著减少复杂度的重构路径。不要只问“这段代码能不能工作”，还要问“有没有更自然的组织方式，让分支、状态、helper、模式或层级直接消失”。

默认把结构质量作为合并风险的一部分处理。用户明确要求严格质量审查、深度 CR、thermo-nuclear review 或 harsh maintainability review 时，提高审查强度，但仍然只输出有证据、可执行、影响合并判断的意见。

## 必问问题

- 是否存在一个更简单的重组方式，可以删除整类条件分支、helper 或模式？
- diff 是否把一次性特例塞进共享路径、繁忙函数或无关模块？
- 变更是否让原本内聚的模块变得更耦合、更有状态或更难扫描？
- 新增抽象是否真正降低理解成本，还是只是薄 wrapper、透传层或身份包装？
- 类型、schema、参数可选性、`any`、`unknown` 或 cast 是否掩盖了真实不变量？
- 逻辑是否放在拥有该概念的 canonical layer，而不是泄漏到调用方或共享细节里？
- 是否重复造了代码库已有的 helper、policy、parser、dispatcher 或转换逻辑？
- 是否把可以独立完成的步骤串行化，或把相关更新拆成可能半应用的状态？
- 文件是否因本 PR 从 1000 行以下膨胀到 1000 行以上，或组件/函数明显越过可扫描边界？

## 强信号

以下情况通常需要 `请求修改`，除非 PR 给出清晰、可信的结构理由：

- 复杂实现保留了大量偶然复杂度，而存在可见的简化路径。
- PR 让文件从 1000 行以下跨过 1000 行，且新增代码可以自然拆分。
- 新增 ad-hoc 分支、模式 flag、nullable mode 或一次性布尔值，使现有流程更缠绕。
- 功能逻辑散落到共享路径，导致兄弟流程语义不一致。
- 新 abstraction、wrapper、cast-heavy contract 或 generic magic 让简单行为变得间接。
- 复制已有 helper 或把逻辑放在错误层级，偏离代码库已有 canonical 设计。
- 更新流程可以留下半应用状态，或独立步骤被不必要地串行编排并增加失败面。

## 首选修复

- 删除一层间接结构，而不是润色它。
- 重塑状态模型，让条件分支消失。
- 把特例变成明确 abstraction、policy、state machine、dispatcher 或 focused module。
- 将逻辑移动到拥有该概念的模块、包、service 或 shared helper。
- 用显式 typed model 或契约替代可选参数、cast 和松散对象形状。
- 抽出纯函数、子组件或小模块，让大文件恢复可扫描性。
- 复用代码库已有 canonical helper，而不是新增近似重复实现。
- 合并重复分支为一条默认流程，只保留必要例外。
- 将相关写入组织成更原子的步骤；独立工作并行化时也要让控制流更清楚。

## 降级边界

不要把纯偏好、命名风格或没有明确收益的大重写当作阻塞项。若只能说“可能更优雅”，但不能指出合并后的维护成本、受影响调用方、复杂度增量或最小可行修复，则不要纳入 finding。
