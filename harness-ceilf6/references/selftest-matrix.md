# 自测场景矩阵

挂在需求 wiki 子文档下的独立子文档，标题 `<短题> · 自测矩阵`，是阶段 3 自测节点逐格执行的依据。正文首行回链需求子文档，其下按本文各节的顺序写：分发面判定 → 矩阵表 → 表前填写约定 → 表后环境准入与版本确认。范例（vc-ai 真实矩阵，结构照此）：https://bytedance.larkoffice.com/wiki/WwzgwKqpPivnVkkxSzdcI6N1nKc#share-F6z2dFuGqoAoSMxU1ekcrACyn7d

## 先定分发面，再画表

同一份代码往往分发到多条产品线：vc-ai 的 web 代码同时被**视频会议、妙记、豆包、文档空间**四条产品线的宿主加载，每条线下又各有若干用户可感知场景（如视频会议线的「会议中 / 尾窗 / 实时字幕」，妙记线的「文字记录 / 实时总结 / 尾窗 / 文字总结」）。凡会加载本次改动代码的产品线全部进表；不需要测试的格子写「未涉及」，不允许直接省掉列——省列无法区分「未涉及」与「漏了」。

从需求上下文与仓库知识列出「哪些产品线 × 哪些端会加载这份代码」；拿不准就全列，让格子说话。

## 每一格的涉及与否必须读源码判定，不许靠推断

「这个端加载了这个模块」**不等于**「这个端会执行到被改的那段」。组件内常按端分叉，各分支用的是不同元素与不同资源——被改的那支可能在某些端上根本不渲染。只按入口层面判断分发面，会把「未涉及」的格子当成待测格，让人花时间去验一个不可能变化的东西；反过来也会漏掉真正受影响的端。

判定动作是固定的三步，**每个改动点、每个端各做一遍**：

1. **定位被改代码的渲染/执行入口**（组件、hook、构建配置项）。
2. **沿调用链找到按端分叉的那个条件**，把每个分支实际用到的元素、类名、资源列出来。分叉常见形态：`isMobile` / `isMobileOrIpad` / `isPC` 三元、`data-layout-mode` 属性选择器、按 `IS_FALLBACK_BUILD` 的构建期常量、主题类 `:global(.theme-dark-mode)`。
3. **对照改动点落在哪一支**：落在该端走的分支才是「待测」，落在另一支就是「未涉及」，并在格子里写明依据（哪个条件、该端走哪支、用的是什么资源）。

写「未涉及」时必须能说出源码依据，不能只写三个字。反面例子：某次把占位背景从 CSS 背景改成 `<picture>`，矩阵给 iOS / Android 都留了待测格；实际源码是 `{isMobileOrIpad ? <div class="placeholder-mobile-static-img"/> : <div class="placeholder-skeleton-layer">…<picture/>…}`，移动端走的是一张未被改动的 SVG，这两格该写成「未涉及（<依据>）」。同一判断在需求过程中错过两次——第一次发现后只在会话里口头更正、没回写矩阵，方案迭代后又照旧犯。

**「该端没有这个功能」和「该端没走到这段改动」是两回事**，判为未涉及时说的必须是后者。上面那个例子里，移动端的占位是存在的、也是产品必需的，只是渲染的元素与资源都不是被改的那一套；把依据写成「移动端没有占位」既不成立，也会让人误以为可以连格子一起删。

**推论一并检查**：若某个端被判为「未涉及」，那么以「覆盖该端」为理由做出的技术选型也随之失去依据，要回到方案层面复核，不能只改矩阵。

## 表结构：两级列头

- 首行 = 产品线，每条线横跨其下场景列（飞书表格用合并单元格；工具不支持合并时列名带产品线前缀，如「妙记·尾窗」——产品线维度不能丢）
- 次行 = 该产品线下的用户可感知场景，从 plan.md 验收标准 + 改动影响面推导，按用户视角命名（「会议中」「尾窗」），不按代码机制（「SW 缓存命中」）
- 行 = 端/环境（iOS / Android / PC，按需加 fallback 替包、旧版本宿主、online/boe 等分发变体）

## 格子状态

- 待测：直接留白，不放占位符
- 未涉及（不需要测试）：写「未涉及（<源码依据>）」，依据要具体到分叉条件与该端实际走的分支，如「未涉及（`isMobileOrIpad` 走 `.placeholder-mobile-static-img`，是未改动的 SVG）」。只写「未涉及」三个字的格子视为未判定
- 测试后符合预期：填 ✅，附截图；通过依赖特殊条件（如主动指定版本）时一句话注明
- 测试后不符合预期：填 ❌，附现象 + 截图 + 初步归因

## 表前：填写约定

- 截图约定：一格多张截图时各代表什么配置态（如「第一张 svs 开、第二张 svs 关」）
- 预期降级行为的通过标准单独注明（如「旧宿主不显示且无报错即为通过」）

## 表后：环境准入与版本确认（必附，缺了矩阵无法执行）

- **准入路径**：每个非自明场景怎么进入——入口操作与前置条件（如「尾窗需开会约 5 分钟且开启 AI 总结才有内容」「豆包走 妙记技能 → 录音转写」）
- **版本切换**：如何让各端加载目标版本（白名单 / query 参数切法，附配置平台链接）
- **版本确认**：如何证明当前加载的就是目标版本（版本标签、探针命令、日志），防止全程在测 fallback 到的旧版本
- **干扰排除**：缓存清除方法、AB 实验优先级高于白名单等会让配置不生效的因素
