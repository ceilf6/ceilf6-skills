# 自测场景矩阵

追加到需求 wiki 子文档的自测执行清单，是阶段 3 自测节点逐格执行的依据。范例（vc-ai 真实矩阵，结构照此）：https://bytedance.larkoffice.com/wiki/WwzgwKqpPivnVkkxSzdcI6N1nKc#share-F6z2dFuGqoAoSMxU1ekcrACyn7d

## 先定分发面，再画表

同一份代码往往分发到多条产品线：vc-ai 的 web 代码同时被**视频会议、妙记、豆包、文档空间**四条产品线的宿主加载，每条线下又各有若干用户可感知场景（如视频会议线的「会议中 / 尾窗 / 实时字幕」，妙记线的「文字记录 / 实时总结 / 尾窗 / 文字总结」）。凡会加载本次改动代码的产品线全部进表；不需要测试的格子写「未涉及」，不允许直接省掉列——省列无法区分「未涉及」与「漏了」。

从需求上下文与仓库知识列出「哪些产品线 × 哪些端会加载这份代码」；拿不准就全列，让格子说话。

## 表结构：两级列头

- 首行 = 产品线，每条线横跨其下场景列（飞书表格用合并单元格；工具不支持合并时列名带产品线前缀，如「妙记·尾窗」——产品线维度不能丢）
- 次行 = 该产品线下的用户可感知场景，从 plan.md 验收标准 + 改动影响面推导，按用户视角命名（「会议中」「尾窗」），不按代码机制（「SW 缓存命中」）
- 行 = 端/环境（iOS / Android / PC，按需加 fallback 替包、旧版本宿主、online/boe 等分发变体）

## 格子状态

- 待测：直接留白，不放占位符
- 未涉及（不需要测试）：写「未涉及」
- 测试后符合预期：填 ✅，附截图；通过依赖特殊条件（如主动指定版本）时一句话注明
- 测试后不符合预期：填 ❌，附现象 + 截图 + 初步归因

## 表前：填写约定

- 截图约定：一格多张截图时各代表什么配置态（如「第一张 svs 开、第二张 svs 关」）
- 预期降级行为的通过标准单独注明（如「旧宿主不显示且无报错即为通过」）

## 表后：环境准入与版本确认（必附，缺了矩阵无法执行）

- **准入路径**：每个非自明场景怎么进入——入口操作与前置条件（如「尾窗需开会约 5 分钟且开启 AI 总结才有内容」「豆包走 妙记技能 → 录音转写」）
- **版本切换**：如何让各端加载目标版本（白名单 / query 参数切法，附配置平台链接）
- **版本确认**：如何证明当前加载的就是目标版本（版本标签、探针命令、日志），防止全程在测 fallback 到的旧版本
- **干扰排除**：缓存清除方法、AB 实验优先级高于白名单等会让配置不生效的因素
