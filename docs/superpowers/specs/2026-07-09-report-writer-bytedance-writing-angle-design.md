# report-writer-bytedance 日报书写角度与审查回路设计

日期：2026-07-09
状态：已与用户逐节确认

## 背景与目标

`report-writer-bytedance` 的数据采集能力（source-map、预检、事件归一化）已被认可，本设计只改书写层。当前产出的问题：像流水账、缺少思考过程、读者口径不清、结构单薄。

日报的读者定位：默认写给本人，同时要能直接作为转正/秋招时展示产出与思考的素材。最终目标是让暑期实习转正与秋招效果最优化。

改动范围：`report-template.md` 重写、`event-schema.md` 扩展、新建 `references/review-panel.md`、`config.yaml` 加一段、`SKILL.md` 加两步。`source-map.md` 与数据采集逻辑完全不动。

## 1. 报告结构与写作角度（report-template.md 重写）

正文从两段变三段：

```markdown
# 今日重点                     ← 新增，0-2 个深度块

## <重点事件标题> —— <一句话价值定位>
- 发现问题：什么信号引出的问题、影响面是什么
- 解决过程：2-4 个关键节点（决策点 + 验证方式），不是操作流水
- 反思沉淀：可复用方法/SOP、踩坑记录、或"重来会怎么做"（三选一，必须有证据支撑）
- 证据：[MR/文档/纪要](url)
- 下一步：（如有）

# 今日完成                     ← 保持现有简洁格式

- <事件>：一句话总结 + 证据链接

# 明日展望

- 1-3 条具体计划
```

Writing Rules 新增：

1. **重点为零则整段省略**：没有含金量的日子不硬凑深度块——空洞的反思比没有反思更减分。
2. **反思必须可执行**：落到具体行为改变或可复用步骤；禁止"学到了很多""收获满满""受益匪浅"类套话（套话黑名单维护在 report-template.md，发布前扫描，命中即阻塞项）。
3. **价值导向表述**：从"完成了 X"升级为"通过 X 解决了 Y"，能量化就量化（耗时、覆盖率、报错量）。
4. **读者口径**：默认写给自己，但按"半年后的自己 / 转正答辩评委能直接看懂"的标准写——不省略背景，缩写首次出现给全称。
5. **SOP 写法**：编号步骤、每步一个动作、含判断条件（"若 X 则 Y"），拿来就能照着执行。

现有规则全部保留：Markdown 链接、无原始 URL、无诊断话术、敏感内容摘要化、禁用口径（TT/ONES/Citadel/大象/美团）。

## 2. 重点事件挑选与事件加工（event-schema.md 扩展）

WorkEvent 新增字段：

```yaml
highlight: true | false          # 是否进「今日重点」
highlight_rationale: string      # 入选理由，写明命中的维度
problem: string                  # 发现问题（信号 + 影响面）
resolution_steps:                # 解决过程关键节点
  - string
reflection: string               # 反思沉淀（方法/踩坑/重来怎么做）
sop_candidate:                   # 可选：值得进沉淀库的 SOP
  title: string
  trigger: string                # 什么场景下用
  steps:
    - string
```

重点事件挑选标准——四个维度，命中 ≥2 个显著信号才够格，每天最多 2 个：

| 维度 | 显著信号示例 |
|------|------|
| 技术深度 | 排查定位、方案设计、技术权衡，而非纯执行 |
| 问题闭环 | 走完"发现→定位→修复→验证"完整链路 |
| 影响面 | 跨人/跨服务协作、止损、解除他人阻塞 |
| 成长信号 | 第一次独立完成某类事、掌握新工具/新领域 |

约束：

- 挑选由主流程判断，`highlight_rationale` 必须写明命中的维度；该理由受 mentor 角色审查，防止把例行工作包装成重点。
- 证据不足以支撑 `problem/resolution_steps/reflection` 三项的事件不得标为 highlight，宁可降级为普通条目。

Draft Mapping 更新：`highlight: true` 渲染成「今日重点」深度块；其余进「今日完成」一行式。发布后触发沉淀库追加（第 4 节）的条件：`sop_candidate` 非空，或 highlight 事件的 `reflection` 属于可复用方法/踩坑且主流程判断值得长期留存。

## 3. 三角色审查回路（新建 references/review-panel.md）

### 角色与审查清单

| 角色 | 视角 | 审查清单要点 |
|------|------|------|
| Mentor（技术导师） | 真实性与深度 | 技术表述是否准确；解决过程是否可信（关键节点齐不齐）；反思是否由证据支撑；SOP 是否可照做；highlight 理由是否成立 |
| 主管（Leader） | 价值与口径 | 每件事的价值定位是否说清（解决了什么、对谁有用）；优先级是否体现；风险/阻塞是否暴露；明日展望是否具体可验收 |
| HR（转正视角） | 成长与表达 | 成长轨迹是否可见；非技术读者能否 30 秒抓住重点；是否体现主动性与协作；这篇作为转正/秋招素材够不够格 |

### 意见格式与分级

每条意见 = `{级别: 阻塞|建议, 位置, 问题描述, 修改建议}`。

阻塞项判定（仅限以下情形，其余一律是建议项）：

- 事实错误
- 无证据支撑的断言
- 空洞套话式反思（命中黑名单）
- 原始 URL / 敏感内容（聊天原文、邮件原文）泄漏
- 禁用口径（TT/ONES/Citadel 等）

### 回路协议

```
起草 → mentor 审 → 主管审 → HR 审（串行，各出意见清单）
  ├─ 无阻塞项 → 发布（建议项择优采纳，未采纳的汇总进助手回复）
  └─ 有阻塞项 → 修订 → 复审（只核对阻塞项是否解决、有无新增阻塞）
       最多 2 轮修订；用尽后仍有阻塞项 → 停止发布，把未解决项列给用户裁决
```

### 双运行时执行方式

- **有子代理能力**（Claude Code）：串行派发三个审查子代理，一次只跑一个、不并行、不隔离工作区；判断不下放——子代理只产出意见清单，采纳/拒绝由主流程决定（对齐 repo-evolver 原则）。
- **无子代理能力**（Codex 等）：同会话内分三个独立阶段自审，每阶段只戴一顶帽子，先输出完整意见清单再统一处理，禁止边审边改。

### 审查输入

草稿全文 + 当日 WorkEvent 记录（含证据清单），审查者据此核对"断言是否有证据"，而非只看文笔。

## 4. 工作流接线、沉淀库、错误处理与验证

### SKILL.md 工作流改动

```

12. 输出契约（扩展：+审查轮次与意见统计、+沉淀库是否追加）
```

### 错误处理

- 沉淀库追加失败：不回滚日报（日报是主交付物），在助手回复中报错并给出待追加内容，用户手动补或下次重试。
- 审查 2 轮后仍有阻塞项：停止发布、列出未解决项等用户裁决。
- 无重点事件的日子：审查回路照常跑（常规条目同样受口径/证据规则约束），预期一轮即过，无特殊分支。

### Safety Checks 新增

发布前扫描反思套话黑名单，命中即视为阻塞项。现有检查（URL 格式、诊断话术、标题/父节点确认、发布后回读）全部保留。

### 验证方式

技能是提示词文件，验证 = 实跑验收。改完后跑一次真实日报生成，检查：

1. 文档呈现三段结构且重点块四要素齐全（或当日无重点时「今日重点」整段省略）；
2. 助手回复包含审查轮次与意见统计；
3. 有 sop_candidate 时沉淀库文档出现带回链的新条目；
4. 无原始 URL、无诊断话术、无套话、无禁用口径。
